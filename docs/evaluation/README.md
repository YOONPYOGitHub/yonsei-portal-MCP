# 실사용 질문·답변 데이터셋 관리

이 폴더는 **공개 질문과 평가 기준**입니다. 실제 계정의 답변·도구 응답은 여기에 저장하거나 커밋하지 않습니다.

- 읽기용 질문 목록: [QUESTIONS.md](QUESTIONS.md)
- 기계 판독용 원본: [questions.jsonl](questions.jsonl)
- 현재 기준: MCP 38개 도구, 질문 152개. 각 도구에 대표·후속·빈 결과/모호함·제한/안전 질문을 마련했습니다.
- 첫 실행은 도구별 대표 질문 하나씩 선택합니다. 다른 질문은 실행하지 않은 상태로 유지하며, 이후 새 실행에서 확장합니다.
- 답변 경로는 현재 대화의 모델 + 실제 MCP 조회입니다. 별도 `.env.llm` 제공자 API를 호출하는 하네스와 구분합니다.

## 1. 질문 계약

각 JSONL 행은 다음 필드를 가집니다.

| 필드 | 의미 |
|---|---|
| `id` | 안정적인 질문 식별자. 기존 ID를 다른 뜻으로 재사용하지 않음 |
| `primary_tool` | 평가 대상 기능. 후속 질문은 다른 도구로 이어질 수 있음 |
| `category` | 기능 분류 |
| `case_type` | `representative`, `followup`, `empty_or_ambiguous`, `boundary_or_safety` |
| `representative` | 첫 대표 실행 대상 여부. 도구별 정확히 하나 |
| `question` | 실제로 답해야 할 한국어 질문 |
| `expected_tools` | 허용·기대되는 도구 경로. 추가 확인/거절에는 빈 목록도 가능 |
| `prerequisites` | 먼저 알아야 하는 식별자·범위·선행 조회 |
| `expected_behavior` | 답변에서 확인해야 할 조건. 실제 개인정보 정답이 아님 |
| `forbidden_claims` | 추정·잘못된 범위·금지 동작 등 |
| `privacy` | 공개/개인 조회 구분. 공개 질문이라도 실제 실행 기록은 기본 비공개 |
| `evaluation_mode` | `answer`, `clarification`, `refusal` |

도구별 네 종류의 기본 질문은 유지하되 후속 사례는 더 추가할 수 있습니다. 질문을 바꾸면 실행 시점의
질문 스냅샷과 해시를 보존합니다. 과거 질문·답변을 최신 문구로 덮어쓰지 않습니다.

## 2. 실행 원칙

1. 사용자가 실행할 질문 ID·모델 경로·개인 조회 범위를 확인합니다. 첫 대표 실행 이후 전체 질문을 자동으로 돌리지 않습니다.
2. 현재 `tools/list`와 질문의 도구 이름·입력을 확인합니다. 문서의 예시 ID를 실제 대상으로 사용하지 않습니다.
3. 강좌·과제·게시판·도서·공지 ID는 실제 선행 조회에서 얻습니다. 대상이 없으면 범위를 임의 확장하지 말고 해당 사례를 `blocked`로 기록합니다.
4. 학교 조회는 순차 실행합니다. 인증/MFA·접근 제한·429가 발생하면 중단하고 사용자에게 요청합니다. 실패를 빈 결과로 바꾸거나 성공할 때까지 반복하지 않습니다.
5. 도구 원문과 수신 시각을 먼저 저장한 뒤 현재 모델이 답변을 작성합니다. 같은 선행 응답을 재사용하면 `reused_call_ids`로 표시합니다.
6. 별도 `.env.llm` 모델로 자동 실행하려면 데이터 전송·API 비용을 다시 확인합니다. 현재 대화 모델 경로와 결과를 섞지 않습니다.
7. 제출·예약·취소·결제 등 쓰기 기능은 실행하지 않습니다. ICS 질문의 파일 저장 금지와 QA 기록 보관은 구분하며 별도 `.ics` 파일/외부 캘린더를 만들지 않습니다.

**평가 한계:** 대표 질문에 정해진 도구 경로를 따라 조회하는 보조 실행은 자유로운 자연어 도구 선택의
블라인드 E2E 평가가 아닙니다. 질문 정의, 조회 경로, 원문 대조, 답변 판단을 별도로 기록해야 합니다.

## 3. 비공개 저장 구조

실사용 기록은 저장소 밖의 사용자 전용 폴더를 권장합니다. 예:

```text
~/Documents/Yonsei-MCP-QA/
  INDEX.md
  index.json
  runs/<run-id>/
    manifest.json             # 모델·시각·MCP 코드 커밋·선택 질문·카탈로그 해시
    catalog_snapshot.jsonl    # 실제 사용한 질문 버전
    calls/<call-id>.json       # 실제 인자·응답·오류 여부·시작/종료 시각
    answers/<question-id>.json # 답변·상태·한계·근거 파일의 SHA-256·재사용 표시
    checkpoint.json           # 종료 시점의 해시 목록·질문·선택·집계
    summary.json              # 집계(실행/미실행/차단/오류를 분리)
    report.md                 # 사람이 읽는 질문·답변 모음
    findings.json             # 후속 원문 검토가 필요한 관찰
    review-v1.json            # 별도 모델/사람 검토. 원래 답변을 변경하지 않음
    integrity.json            # 내보낸 파일의 체크섬 목록(선택)
```

- POSIX 디렉터리는 `0700`, 파일은 `0600`으로 보호합니다. Windows의 mode 값은 ACL 보호를 증명하지 않습니다.
- 파일명·매니페스트에 비밀번호·학번·실명을 넣지 않습니다. API 키·쿠키·인증 헤더·환경변수 전체는 기록하지 않습니다.
- **실제 도구 응답은 개인정보가 제거된 자료가 아닙니다.** 등록번호 등을 답변에서 제외해도 원문에는 남을 수 있습니다.
- 개발 중 `.hermes/evaluation-runs/`를 사용하면 Git에서 제외되지만, 장기 보관본은 저장소 밖에 두는 편이 안전합니다.
- 기존 기록을 덮어쓰지 않습니다. 재실행은 새 run-id를 만들고 필요하면 매니페스트에 이전 실행 ID를 연결합니다.
- 설명 수정만 하는 경우에도 새 실행을 만들고 `execution_mode`에 과거 근거 재사용임을 표시합니다. 원래 시각·출처 실행 ID·해시를 유지하고 새 MCP 조회 횟수는 0으로 구분합니다. 저장된 호출 기록 수를 새 조회 횟수라고 보고하지 않습니다.
- 보관 기한·삭제·공유는 소유자가 결정합니다. 공개 배포 전에 익명화·동의를 별도로 검토해야 하며 secret scanner 통과가 개인정보 제거를 보장하지 않습니다.

## 4. 기록 도구

`tests/qa/records.py`는 **저장·검증만** 담당하는 개발 보조 도구입니다. 모델을 호출하거나 학교에 로그인하지 않습니다.

- `RunStore.create(base_path, manifest)`: 새 실행 폴더를 생성합니다. `timestamp`, `model`, `execution_mode`는 호출자가 실제 값으로 제공합니다.
- `save_call(call_id, record)`: 실제 호출의 `tool`, `arguments`, `result`, `is_error`, `started_at`, `finished_at`을 저장합니다.
- `save_answer(question_id, record)`: 답변 상태·내용·`call_ids`·`reused_call_ids`를 저장하고 근거 해시를 생성합니다.
- `summarize(catalog, selected_ids)`: 누락·알 수 없는 질문·허용하지 않은 도구·근거 변조·재사용 미표시를 검사합니다.
- `seal_run(store, catalog, selected_ids)`: 종료 스냅샷을 남깁니다. 이후 같은 실행의 호출/답변 추가는 거절합니다.
- `verify_archive(path)`: 원래 프로세스가 종료된 뒤에도 **핵심 기록**(manifest·calls·answers·체크포인트 내부 질문/집계)의 체크섬·근거·집계를 읽기 전용으로 확인합니다. 별도 Markdown·스냅샷·리뷰 파일은 이 함수의 검증 대상이 아닙니다.
- `verify_full_archive(path)`: `integrity.json`에 열거한 **전체 내보내기 파일**의 SHA-256 및 누락·추가 파일을 검사합니다. 루트 `integrity.json` 자신을 제외한 모든 파일을 포함해야 합니다. 핵심 기록의 의미·집계 검증을 대신하지 않으므로 두 함수를 함께 사용합니다.
- 새 체크포인트는 버전 2이며 `refused` 개수를 명시합니다. 버전 1의 기존 기록은 파일을 변경하지 않고 누락된 거절 개수만 0으로 해석해 검증합니다.

실행 중에는 하나의 `RunStore` 객체를 유지합니다. 중단한 실행에 몰래 덧붙이지 않고 새 실행에서 이어서 수집합니다.
핵심 JSON 기록과 체크포인트·인벤토리는 최대 4 MiB이며 초과·유효하지 않은 JSON·경로 이탈·심볼릭 링크·덮어쓰기는 거절합니다. 전체 내보내기 검사에서 일반 파일은 크기가 아닌 스트리밍 청크로 해시를 계산합니다.

저장소 루트의 개발 환경에서 아카이브 확인(실제 실행 ID로 교체):

```bash
uv run --no-sync python -c "from pathlib import Path; from tests.qa.records import verify_archive; print(verify_archive(Path.home() / 'Documents/Yonsei-MCP-QA/runs/<run-id>'))"
```

해시는 자료가 나중에 바뀌었는지 확인하는 수단이지 원격 호출·답변 정확성의 증명이 아닙니다.
파일과 체크포인트를 함께 바꿀 수 있는 소유자 공격이나 적대적 동시 파일 변경까지 방어하는 저장소는 아닙니다.
기록 API의 입력을 임의로 만들어 실제 실행인 것처럼 저장해서는 안 됩니다.

## 5. 상태·검토 기준

| 상태 | 의미 |
|---|---|
| `answered` | 실제 허용된 도구 근거로 답변을 작성함. 정확도 합격 점수는 아님 |
| `tool_error` | 도구 오류 근거가 남아 있음. 정상 0건과 구분 |
| `blocked` | 대상 부재·선행 조회 실패·권한 문제 등으로 해당 경로를 실행하지 못함 |
| `needs_clarification` | 식별자·범위·공식 시각 등 추가 정보가 필요하거나 미확인 값의 해석을 설명함 |
| `refused` | 금지·미지원 요청을 명시적으로 거절함. 답변과 이유가 필요하며 안전 거절 질문의 `expected_tools=[]`이면 호출 근거를 만들지 않음 |
| `not_run` | 선택했지만 아직 답변 기록이 없거나, 이번 실행에서 선택하지 않음 |

`selected_counts`와 `unselected_not_run`을 따로 봅니다. 도구 호출 수, 질문 수, 실제 사용한 도구 종류 수는 서로 다릅니다.
표시된 호출 횟수는 네트워크 요청 횟수와도 다릅니다. 하나의 MCP 호출이 여러 페이지 조회를 수행할 수 있습니다.

검토 체크리스트:

- 질문의 대상·기간·필터와 실제 인자가 일치하는가?
- 숫자·날짜·이름·링크가 해당 근거에 있는가? 미확인 값을 0·없음으로 바꾸지 않았는가?
- 목록·본문·이미지·첨부, 표시 페이지·전체 이력을 구분했는가?
- 신청학점·취득학점, LMS 점수·ERP 성적, 학기 필터·전체 누적을 혼동하지 않았는가?
- 좌석 표시 수치를 실제 이용 가능성으로 단정하지 않았는가?
- 테스트용 교시 매핑을 학교 공식 시각으로 소개하지 않았는가?
- 이름·학번·등록번호 등 제외 요청과 읽기 전용 범위를 지켰는가?
- 답변과 근거가 달라지면 기존 파일을 수정하지 않고 검토 이력/새 실행으로 남겼는가?

공개 Markdown과 JSONL의 질문·기대 동작·도구 경로·모드·개인정보 분류·링크·집계는 오프라인 회귀 검사로 동기화를 확인합니다. 질문 문서는 실행 현황이 아니므로 미실행/성공 여부는 개별 실행 기록에서 확인합니다.

모델 자체 점검·독립 모델 검토·사람 검토를 구분합니다. 빈 결과나 기능 한계를 정확하게 설명한 답변을
무조건 실패로 처리하지 않고, 반대로 자료를 가져왔다는 이유만으로 정확한 답변이라고 판정하지 않습니다.
